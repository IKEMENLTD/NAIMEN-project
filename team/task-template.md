# TASK-TEMPLATE.md - タスク指示テンプレート

## すべてのタスクに含めるべき指示

```markdown
---
## 🧠 思考モード: DEEP

**コンテキスト最適化:**
- `team/context-optimization-strategy.md` を参照
- 必要なファイルだけを読む（全ドキュメントを読まない）

**必読プロトコル:**
- `team/deep-thinking-protocol.md` を読んでから作業開始
- `team/review-protocol.md` でレビュー基準を確認

**📂 読むべきファイル（タスク固有）:**
[CTOがタスクごとに明示する]

**必読:**
- QUICK-REF.md（プロジェクト全体像）
- [タスク固有のファイル2-3個]

**オプション（必要に応じて）:**
- [詳細ドキュメント]

**不要:**
- その他のresearch/docs配下（このタスクには無関係）

**思考の深さ要件:**
- Level 4以上（トレードオフの明示）を目指す
- 「なぜ？」に3回以上答える
- 代替案を3つ以上検討する
- エビデンスの強度を評価する
- 不確実性を正直に認める

**成果物の要件:**
- 前提と制約を明示
- 検討した選択肢を列挙
- 判断基準を明確化
- トレードオフを説明
- 不確実性を記載
- 次の問いを提示

**時間配分:**
- 情報収集: 20%
- 思考・検討: 50% ← 最重要
- 文書化: 25%
- 自己レビュー: 5%

**自問自答する質問:**
1. この主張を支持するエビデンスの強度は？
2. 反対する研究結果はないか？
3. 技術的実現可能性は？
4. コストは？（時間・費用・リスク）
5. これは誰を利するか？誰に不利益か？
6. ユーザーにとっての価値は何か？
7. **なぜこれをやるのか？**
8. **本当に必要か？**
9. **どうなれば成功か？**
10. **最大のリスクは何か？**

---
```

**タスク:** Big Fiveの評価システム設計

🧠 **思考モード: DEEP**（team/deep-thinking-protocol.md参照）

**コンテキスト:**
- 日本人ユーザー向け内面測定システム
- 科学的厳密性とユーザー体験の両立が必要
- MVP段階（予算・時間制約あり）

**設計すべきもの:**
1. Big Five測定の具体的手法（尺度選定）
2. スコアリングアルゴリズム
3. 結果表示の透明性設計

**制約条件:**
- 評価時間: 15分以内
- ライセンス: オープンソース優先
- 科学的妥当性: 予測妥当性 r ≥ 0.50

**思考すべき問い:**
- NEO-PI-R vs BFI vs IPIP: どれが最適か？（トレードオフ比較）
- 日本語版の文化的妥当性は？
- 短縮版を使う場合、予測妥当性はどの程度低下するか？
- ユーザーが結果を信頼できる説明方法は？

**成果物:**
`docs/bigfive-design.md` に以下を含める:
- 前提と制約
- 検討した選択肢（3つ以上）
- 判断基準と最終判断
- トレードオフの明示
- 不確実性の記載
- パイロット研究での検証計画

**深く考えてください。表面的な答えは不要です。**
```

**タスク:** Phase 2設計の深層レビュー

🧠 **思考モード: DEEP**（team/deep-thinking-protocol.md参照）
📋 **レビュー基準:** team/review-protocol.md

**レビュー対象:**
1. research/内面測定_科学的調査レポート.md
2. docs/architecture.md
3. docs/project-plan.md

**レビュー観点（優先順）:**
1. 科学的根拠の強度（30点）
2. 実装可能性（25点）
3. 倫理性・公平性（20点）
4. ユーザー体験（15点）
5. 完全性（10点）

**特に深く検討すべき点:**
- 文化的妥当性（日本人への公平性）
- ライセンス問題（法的リスク）
- 「上位20%」定義の科学的根拠
- MVPスコープの現実性

**レビューの深さ要件:**
- 単なる指摘ではなく、「なぜ問題か」を説明
- 代替案を具体的に提示
- エビデンスを引用
- 改善後の予測品質を推定
- 不確実性を明示

**成果物:**
`reviews/phase2-review-round1.md` に以下を含める:
- 総合評価（点数とグレード）
- 致命的問題（P0）のリスト
- 重大な問題（P1）のリスト
- 改善提案（具体的アクション）
- 優れている点の明示
- 改善後の予測品質

**スタンス:** 批判的だが建設的。妥協しない。

**自問自答:** 「このまま実装して、上位20%のシステムが作れるか？」
```

## 多段階レビューの実装

```markdown
### Round 1: 初期レビュー（致命的問題の検出）
- Reviewerが第1段階レビュー実施
- 致命的問題（P0）があれば即座に修正タスク発行
- → Researcherが深掘り調査
- → 修正版を再提出

### Round 2: 深層レビュー（本質的改善）
- 修正版を再度Reviewerがレビュー
- 本質的問題（P1）を洗い出し
- → Architectが再設計
- → 修正版を再提出

### Round 3: 最終検証（完璧性の追求、必要時のみ）
- エッジケース、パフォーマンス、セキュリティ詳細を検証
- 承認 or 微調整
```

## 実装方法

CTOがタスク発行時に、このテンプレートを参照して詳細な指示を作成する。

すべてのサブエージェントに「深く考える」文化を浸透させる。
