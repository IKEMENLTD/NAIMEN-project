# CONTEXT-OPTIMIZATION-STRATEGY.md - コンテキスト最適化戦略

## 問題の本質

**現状:**
- プロジェクト文書: 157KB（8ファイル）→ 200KB超予定
- Clawdbotの自動切り詰め: 20KB/ファイル
- 8ファイル × 20KB = **160KB** がワークスペース注入だけで消費
- Claude Sonnet 4.5のコンテキスト: 200K tokens（約50KB/1万token換算で最大500KB相当）

**問題:**
- サブエージェントが毎回全ドキュメントを読むと、思考に使えるトークンが減る
- 詳細設計・実装フェーズに入るとさらに増える
- コスト増大（cache利用でも）

## 解決策（5段階）

### Level 1: 階層的ドキュメント構造 ⭐⭐⭐⭐⭐

**概念:**
```
プロジェクトルート
├── README.md                    ← 2KB: 全体像・ナビゲーション
├── QUICK-REF.md                 ← 5KB: 主要決定事項のサマリー
├── docs/
│   ├── architecture.md          ← 60KB: 詳細設計（必要時のみ読む）
│   └── architecture-summary.md  ← 10KB: 要約版
├── research/
│   ├── _INDEX.md                ← 3KB: 調査レポート一覧
│   └── [詳細レポート群]         ← 必要時のみ読む
```

**効果:**
- ワークスペース注入: README + QUICK-REF + _INDEX = **10KB以下**
- 詳細は**必要時のみ**タスク指示で明示的に読む

**実装:**
```markdown
**タスク指示例:**
「アーキテクチャを修正してください。
まず `docs/architecture-summary.md` を読んで全体を把握し、
必要に応じて `docs/architecture.md` の該当セクションを読んでください。」
```

---

### Level 2: エグゼクティブサマリー自動生成 ⭐⭐⭐⭐

**概念:**
各主要ドキュメントに自動生成の要約セクションを追加。

**フォーマット:**
```markdown
# [Document Title]

## 📋 エグゼクティブサマリー（300語以内）
[本質的な決定事項、トレードオフ、次のアクション]

## 📊 主要メトリクス
- スコア: 85/100
- 修正回数: 2回
- 最終承認日: 2026-01-27

## 🔗 関連ドキュメント
- 依存: research/内面測定.md
- 影響: project-plan.md

---
[詳細内容は以下...]
```

**効果:**
- エージェントは**サマリーだけ読めば**80%理解できる
- 詳細は必要時のみ

**実装:**
フェーズ完了時にReviewerまたはPMがサマリーを生成。

---

### Level 3: タスク固有のコンテキスト指示 ⭐⭐⭐⭐⭐

**概念:**
タスク指示で「何を読むべきか」を明示する。

**例:**

❌ **悪い指示:**
```
フロントエンドを実装してください。
（→エージェントは全ドキュメントを読もうとする）
```

✅ **良い指示:**
```
**タスク:** ログインフォームの実装

**必読:**
- docs/architecture-summary.md（全体構造）
- docs/frontend-design.md セクション3.2（フォーム仕様）

**オプション:**
- research/内面測定.md（評価項目の理解が必要な場合のみ）

**不要:**
- その他のresearchレポート（このタスクには無関係）
```

**効果:**
- 読むべきファイルを**3-5個に限定**
- 不要な文書をコンテキストから排除
- トークン消費 **80%削減**

---

### Level 4: 定期的なドキュメント統合・圧縮 ⭐⭐⭐

**概念:**
フェーズ完了時に、複数の文書を統合して重複を削除。

**例: Phase 2完了時:**
```
Before:
- research/内面測定.md (18KB)
- research/cultural-validity.md (27KB)
- research/license-analysis.md (15KB)
- research/top20-definition.md (12KB)
合計: 72KB

After:
- research/phase1-consolidated.md (35KB)
  ├── セクション1: 内面測定の科学的根拠
  ├── セクション2: 文化的妥当性
  ├── セクション3: ライセンス分析
  └── セクション4: 上位20%定義
- research/_ARCHIVE/ ← 元ファイルを退避
```

**効果:**
- 重複削除（各レポートの「背景」「方法論」は共通）
- サイズ **50%削減**
- ナビゲーション改善

**実装:**
PMまたはReviewerがフェーズ完了時に統合タスクを実行。

---

### Level 5: キャッシュ戦略の最適化 ⭐⭐⭐

**概念:**
Claudeのprompt cachingを最大限活用。

**Clawdbotの自動cache:**
- システムプロンプト（ワークスペースファイル含む）は自動でキャッシュ
- 変更がなければ再利用 → コスト75%削減

**最適化:**
1. **不変ドキュメントを前に配置:**
   - AGENTS.md, SOUL.md → めったに変わらない → 常にキャッシュヒット
   - STATUS.md → 頻繁に変わる → キャッシュミス

2. **変更頻度で順序を制御:**
   ```
   ワークスペース注入順序（理想）:
   1. AGENTS.md（不変）
   2. SOUL.md（不変）
   3. TOOLS.md（不変）
   4. IDENTITY.md（不変）
   5. USER.md（不変）
   6. QUICK-REF.md（週1更新）
   7. STATUS.md（毎回更新）← これだけキャッシュミス
   ```

**効果:**
- キャッシュヒット率 **90%以上**
- 実質的なコンテキストコストが **1/10**

**制限:**
Clawdbotの注入順序は固定（変更不可）。
ただし、タスク指示での明示的な`read`は制御可能。

## 長期戦略（Phase 3: 実装フェーズ）

### コードが増えたら

**問題:**
- src/ 配下に実装コードが増える
- TypeScript/React等で数百ファイル

**対策:**
1. **コードはワークスペース注入しない**
   - AGENTS.mdにコード構造の概要だけ記載
   - 実装タスクでは必要なファイルだけ`read`

2. **コードサマリー生成**
   ```bash
   # 自動生成ツール
   tree src/ > docs/code-structure.txt
   cloc src/ > docs/code-stats.txt
   ```

3. **AI Code Review用の軽量表現**
   - 関数シグネチャのみ抽出
   - 型定義のみ抽出
   - 詳細実装は必要時のみ読む
